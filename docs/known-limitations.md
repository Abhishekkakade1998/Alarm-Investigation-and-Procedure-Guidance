# Known Limitations

This repository is a local development and assignment prototype, not a
production industrial-control application.

## Data, evidence, and operational safety

- The simulator contains synthetic data only. Results do not represent a live
  plant, ABB equipment, or actual alarm state.
- Its 90-day alarm fixture repeats each alarm template three times, 30 days
  apart. Recurrence counts and severity progression are test/demo behavior,
  not evidence of a real operating trend.
- The included procedure documents are sample corpus content. Simulator
  recommendations are generic, and returned document-reference labels are not
  verified document citations.
- Generated answers can be incomplete or incorrect. Do not use them to change
  operating conditions or replace approved site procedures, limits, or
  operator judgment.
- Retrieval is based on local vector similarity and a configured threshold;
  relevance and citations depend on corpus quality and indexing.
- Incremental re-ingestion does not remove prior chunks for a changed document;
  rebuild the full local index after document updates to avoid stale content.

## Security and operations

- The simulator uses a configurable bearer token, with a demo fallback for
  local setup. The copilot API and MCP SSE endpoint do not authenticate
  individual users or enforce per-tool authorization.
- TLS, OAuth/SAML, rate limiting, audit retention, centralized secret
  management, and network policy are not implemented.
- Logs are not a complete observability pipeline. Backend response timings and
  simulator trace context are available, but centralized metrics, distributed
  tracing, alerting, and structured JSON logs are not configured.
- The calculation API stores jobs in process memory; job state is lost on
  restart and is not shared across replicas.
- Qdrant local storage is intended for a single process. It is not suitable
  for concurrent multi-replica production use.
- Docker Compose wiring is provided but has not been validated in an
  environment without Docker Desktop. Local Python tests do not require Docker.

## Model, latency, and workflow

- Answer quality and response time depend on local Ollama availability, model
  choice, CPU/GPU capability, and the number of tool rounds. The timeout is a
  maximum wait, not a latency target.
- The chat interface forwards only a bounded recent history. It does not
  persist conversations as server-side sessions.
- The simulator exposes several analytics endpoints that are not currently
  callable as MCP tools from the copilot.
- The acceptance integration test runs the real simulator and MCP tool handler
  in-process with deterministic RAG and LLM fixtures. It does not launch the
  full Streamlit, backend, MCP, simulator, vector store, and Ollama stack as
  one browser-driven test.
- CI currently runs Python compilation and the unit, integration, and MCP test
  suites with coverage. No formatter, linter, static type checker, or
  dependency/security scanner is configured.

## Submission evidence

- A demo video and screenshots must be recorded from a running environment;
  they are not generated by automated tests and are not included here.
- The test coverage report records line coverage only; it is not evidence of
  operational safety or answer quality.
